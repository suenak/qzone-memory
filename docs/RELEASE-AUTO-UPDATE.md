# 版本更新：检查、发布与下载引导

本文说明客户端如何检查新版本，以及如何发布一个版本。

**客户端不做自动安装。** 更新流程是：请求清单 → 比对版本 → 有新版就弹窗展示更新内容 → 用户点「前往官网下载」→ 由用户自己下载安装包覆盖安装。这样既不需要在客户端内置签名公钥，也不需要 Android 的「安装未知应用」权限，用户还能在动手前看清这次改了什么。

检查有**两个入口**：应用启动时静默检查一次（有新版才弹窗，其余情况一概不打扰），以及设置 → 关于 → 应用更新里的手动检查。两者共用同一个弹窗与同一份状态。

---

## 1. 机制

| 环节 | 说明 |
| --- | --- |
| 触发 | 启动时自动静默检查一次；用户也可以随时在 设置 → 关于 → 应用更新 里手动检查 |
| 清单 | `GET <更新服务>/api/v1/update/latest`（也兼容 `/:target/:arch/:version` 动态端点） |
| 比对 | 客户端把清单的 `version` 与自己版本号按数字段比较 |
| 无更新 | 服务端返回 **204**,客户端**不做任何提示**（启动检查）或提示「当前已是最新版本」（手动检查） |
| 请求失败 | 启动检查**保持沉默**;手动检查才提示失败原因 |
| 有更新 | 弹窗显示版本号与 `notes`,按钮跳转到 `download_page` |
| 安装 | **由用户完成**：从官网下载安装包，覆盖安装 |

清单格式：

```json
{
  "version": "1.2.0",
  "notes": "更新内容，支持换行",
  "pub_date": "2026-10-10T00:00:00Z",
  "download_page": "https://你的官网/download",
  "platforms": {
    "windows-x86_64": { "signature": "", "url": "https://.../qza-1.2.0-setup.exe" },
    "android": { "signature": "", "url": "https://.../qza-1.2.0.apk" }
  }
}
```

`platforms` 与 `signature` 沿用 Tauri 的字段名以便将来接官方 updater；当前客户端**不读**它们——用户不通过应用下载，`url` 只是留给以后可能的用途。真正驱动流程的是 `version`、`notes` 和 `download_page`。

## 2. 一次性配置

### 2.1 客户端：更新清单地址

地址不写在源码里。`src-tauri/src/updater.rs` 只做了一层 `pub use` 别名，真正的值由
`src-tauri/build.rs` 在构建期从配置读出：

```jsonc
// src-tauri/qza.config.json（入库，占位值）或 src-tauri/qza.config.local.json（不入库，真实值）
{
  "QZA_UPDATE_ENDPOINT": "https://你的域名/api/v1/update/latest",
  "QZA_DOWNLOAD_PAGE": "https://你的官网/"   // 兜底地址
}
```

取值优先级：编译期环境变量 > `qza.config.local.json` > `qza.config.json`。仓库里带的是
`https://updates.invalid/...`——**故意不可解析的保留域名**，克隆下来能编译但不会连到任何真实服务。

> 发布构建必须在打包机上提供 `qza.config.local.json`（或设置同名环境变量），否则打出来的包指向占位地址、无法激活。四项全为占位值时 `build.rs` 会发 `cargo:warning`，客户端也会明确提示「本构建未配置授权服务器」。

`DOWNLOAD_PAGE` 是兜底：清单里带了 `download_page` 时以清单为准，这样改下载页不需要重新发客户端。

客户端通过 Rust 的 `fetch_update_manifest` 命令读取固定地址，超时为 10 秒，清单上限为 512 KiB。
请求不携带 QQ Cookie 或授权凭据，不依赖 WebView 的 CSP/CORS，也无需开放任意域名访问权限。
地址应直接返回清单，不使用 HTTP 重定向。

### 2.2 服务端：下载页地址

```
QZA_DOWNLOAD_PAGE=https://你的官网/download
```

不配置时清单不带该字段，客户端回退到自己内置的兜底地址。

建议同时设置 `QZA_PUBLIC_URL`,否则安装包地址按请求 `Host` 推导，反代改写 Host 时会拼出客户端访问不到的域名。

## 3. 发布一个版本

**第一步：构建**

```bash
npm run tauri:build:windows        # Windows 安装包
npm run tauri android build        # Android APK
```

**不需要签名**——客户端不验签，构建时也就无需 `TAURI_SIGNING_PRIVATE_KEY`。

**第二步：上传**

打开 `http://<你的服务>/admin` → 顶部页签「客户端版本」:

1. 填版本号与更新说明，保存。说明会原样出现在用户的弹窗里，**支持换行**,建议分条写清改动。
2. 对应平台一行点「上传安装包」。
3. 点「发布」。

版本号必须与客户端里的 `1.1.0` 这类**数字点分形式**一致——客户端只按前三段数字比较，带 `-beta` 之类后缀的版本号会被判为「不更新」。

**第三步：验证**

```bash
curl "https://你的域名/api/v1/update/latest?version=<上一个版本>"
```

应返回带 `version` / `notes` / `download_page` 的 JSON。用当前版本号请求同一地址应得到 **204**。

## 4. 常见问题

**点了检查却没反应，或提示检查失败**
检查清单地址是否可达、是否 https、证书是否有效。客户端不做任何降级——请求失败只会提示重试，不会静默当作「已是最新」。

**一直提示已是最新，但明明发了新版**
核对清单返回的 `version` 与客户端实际版本。版本号必须是纯数字点分；另外客户端只在**点击检查**时比对，不会后台轮询。

**用户点击「前往官网下载」打开的是错误地址**
优先看清单里的 `download_page`（服务端的 `QZA_DOWNLOAD_PAGE`）;该字段缺失时才会用到客户端内置的 `DOWNLOAD_PAGE`。

**想撤销一次发布**
后台点「撤销发布」,清单立即回到 204,已经看到弹窗的用户不受影响（他们本来就只是去官网下载）。

## 5. 已知限制

- **不检测更新是否安装成功**。用户去官网之后的一切应用无从得知，也没有「已更新到 vX」的回执。
- **启动只检查一次，运行期间不轮询**。应用长时间开着时，期间发布的新版本不会被发现，需要重启或手动点一次「检查更新」。
- **macOS 未纳入发布**：安装包构建配置里有 dmg，但本文流程只覆盖 Windows 与 Android。
- 本文流程**没有在真实发布中端到端跑过**：服务端接口有 98 项端到端测试覆盖（含 204 语义、清单字段、下载与限流），客户端逻辑通过类型检查与构建，但「构建 → 上传 → 客户端检查 → 弹窗 → 跳转」这条链路需要你第一次发版时实测一遍。
