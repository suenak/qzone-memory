# 版本更新内容规范

本文件规定「版本更新内容」怎么写。同一份内容会分发到四个地方，写法必须先在源头统一。

参考实现：`deepseek-ai/deepseek-harness` 的 Release 正文（固定四分类、条目单行、句末句号、无 emoji）。

## 一处源头

版本更新内容只有一个源头：仓库外的 `output/notes-<版本>.md`（`output/` 不入版本控制）。

发布流水线 `output/release.ps1` 读它，再分发到四处：

| 消费端 | 内容形态 | 由谁写 |
| --- | --- | --- |
| 客户端「应用更新」弹窗 | 全文（含分组标题），纯文本换行渲染 | `notes` 阶段 → 服务端 `releases.notes` |
| GitHub Release 正文 | 只保留 `- ` 条目，分组标题丢弃 | `bump` 阶段 → `.github/workflows/release.yml` |
| `CHANGELOG.md` | 全文，分组标题转成 `**加粗行**` | `bump` 阶段 |
| `README.md` | 只取摘要句，替换「当前版本」那行的描述 | `bump` 阶段 |

不要在 `CHANGELOG.md` 或 GitHub 网页上直接改：下次原地重发会被 `notes-<版本>.md` 覆盖。

## 文件格式

```markdown
# 拾忆 1.2.9

> 一句话摘要，说明本版最重要的一两件事，句末句号。

新增功能

- 一条一件事，单行，句末句号。
- 第二条。

问题修复

- 修了什么、原来错在哪、现在是什么行为。

体验优化

- 界面或性能上的改进。

其他变更

- 文档、构建、依赖、许可之类的变更。
```

- 第一行 `# 拾忆 <版本>` 只作标题，会被剥掉。
- `> ` 开头的一行是摘要，会被抽出来单独使用。
- 分组标题是**纯文本行**（不带 `#`、不带 `**`）。带 `#` 的行会被剥掉；带 Markdown 标记会原样出现在客户端弹窗里。
- `<!-- -->` 注释块整段会被剥掉，可以拿它当模板里的使用说明。
- 其余非空行按原样保留。

## 四个固定分组

顺序固定，**空的分组不写**：

1. `新增功能` —— 用户能用的新能力
2. `问题修复` —— 修掉的错误
3. `体验优化` —— 交互、布局、性能、体积
4. `其他变更` —— 文档、构建、依赖、许可

不要自造分组名。分组只在客户端弹窗与 `CHANGELOG.md` 里出现，GitHub Release 正文里没有。

## 条目写法

- `- ` 开头，**单行**，**句末句号**。
- 一条一件事。同一件事的前后两半用「；」连接，不要拆成两条。
- 写「哪里变了、变成什么」。「修复了若干问题」不算内容。
- 面向用户：写「说说页图片一直显示『等待加载』」，不写「修复 image observer 注册时机」。
- 不写 commit hash、PR 号、文件名、函数名、`src/` 路径。
- 不写「未发布」「本地构建」「待验证」这类状态说明；版本发没发由版本号本身表达。
- 中英文与数字之间留一个空格；中文标点用全角；代码标识符用反引号。

## 摘要写法

- 一行，≤ 60 字，句末句号。
- 说本版最重要的一两件事，不是条目列表的复述。
- 它会出现在 `README.md` 的「当前版本」那行，也会拼进 GitHub Release 顶部的固定说明句后面。

## 长度预算

- 服务端上限 **4096 字节**（`license-server/src/releases.js` 的 `MAX_NOTES_BYTES`），超了会拒绝发布。
- 建议正文控制在 **2000 字节**以内（约 12–15 条），单条 ≤ 200 字节。
- 客户端弹窗是纯文本渲染，太长会变成一堵墙。写不下就说明这版该拆了。

## 发布流程里的检查

`output/release.ps1` 的 `notes` 阶段会校验，模板见 `output/notes-template.md`：

拦下来的（不通过就直接停，不会带着不合规的说明往下发）：

- 至少一个分组标题，且分组名都在四个固定名字里、不重复。
- 至少一条 `- ` 条目，每条单行、句末带标点、≤ 200 字节。
- 正文不超过 4096 字节（服务端硬上限）。
- 不出现 `未发布` / `本地构建` / `待验证` 之类的状态词。

只警告的（照发，但该改）：

- 正文超过 2000 字节的建议值。
- 没有 `> ` 摘要行，或摘要超过 60 字。
- 分组顺序与规范不一致。

## 例外

- 摘要可以留空：GitHub Release 顶部的固定说明句会保持原样，`README.md` 那行的描述也不动。但正常发布都应写。
- 首个公开版本或大版本可以在正文最前面加一句引导语（说明这版汇总了哪个区间），单独成段，不加 `- `。

## 为什么不用 commit 生成

`CHANGELOG` 与 Release 正文里的条目是写给用户看的，不是给开发者看的。从 commit 或 PR 标题生成只会得到「chore(release): 版本 1.2.8」这类没有信息量的行。GitHub 的 `generate_release_notes` 仍会附上自动的 `What's Changed` 段落，那是补充，不是正文。
