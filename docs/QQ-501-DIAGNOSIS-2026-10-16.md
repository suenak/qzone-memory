# QQ 空间 HTTP 501 实测排查

按检索匹配的 [morluto/rea](https://github.com/morluto/rea) 参考其[浏览器观测](https://github.com/morluto/rea/blob/main/docs/browser-observation.md)和[网络捕获](https://github.com/morluto/rea/blob/main/docs/web-network-captures.md)方法，对照路由、网络栈和会话参数。本机没有运行 REA MCP；本次使用原生 Rust 诊断和 Windows curl 做受控对照，没有做浏览器流量捕获。

## 实测结果

仅执行只读小页请求。凭证由 Rust 内部读取；诊断只输出接口代号、路由、HTTP 状态、WAF 标记和业务错误码。未输出 Cookie、令牌、带令牌的 URL 或响应正文。

| 条件 | 历史消息 | 互动通知 |
| --- | --- | --- |
| 保存会话，reqwest，环境代理 | 501，腾讯 WAF | 501，腾讯 WAF |
| 保存会话，reqwest，直连 | 501，腾讯 WAF | 501，腾讯 WAF |
| 保存会话，Windows curl / Schannel，直连 | 501，腾讯 WAF | 未测试 |
| 匿名，reqwest，直连 | 200，非 WAF | 未测试 |
| 不带 Cookie，仅请求令牌，直连 | 200，非 WAF | 未测试 |
| 仅当前 Cookie，不带请求令牌，直连 | 501，腾讯 WAF | 未测试 |
| 去掉 pt4_token 的核心 Cookie 组合 | 501，腾讯 WAF | 未测试 |
| uin+skey 或 uin+p_uin+p_skey 子集 | 均为 501，腾讯 WAF | 未测试 |

Python 匿名对照中，两接口在直连和代理路径均为 HTTP 200，业务码分别为未登录或缺少合法参数。匿名响应不证明已登录数据可读取。

此处“直连”仅指客户端禁用 HTTP 环境代理，没有验证系统 TUN 或实际出口 IP，不能据此排除全部网络因素。

## 用户重新网页登录后的复测

用户确认已在拾忆内完成 QQ 网页登录后，再次从系统凭据库读取当前会话。历史消息、互动通知在两条客户端代理配置下仍为 501；Windows Schannel 对照也为 501，匿名及仅令牌对照仍为 200。当前证据不支持“重复登录一次即可恢复”的结论。

已打开独立浏览器的官方 `https://i.qq.com/` 页面，实际可见扫码登录入口，尚待用户进入个人空间。客户端中的网页登录与这个浏览器配置的会话不能视为共享。尝试启用浏览器 CDP 网络观察超时，没有取得官方页面登录后的请求记录，不能将此步骤记为浏览器流量验证成功。

## 官方页面确认与客户端登录修复

用户随后完成独立浏览器登录。实际页面已显示个人中心、空间资料、动态正文和评论，确认官方页面当前可以读取内容；没有取得该页面的逐接口 HTTP 状态，不能据此保证旧历史或移动互动接口可用。

代码另发现可独立修复的缺陷：桌面网页登录原先读取 `i.qq.com` 的 Cookie，缺少 p_skey 时混合整个 WebView 的 Cookie，没有区分 QQ 子域或确认页面已进入空间。它也复用原有 WebView 会话，可能在重新登录前就捕获旧凭证。现在使用独立隐私窗口，等待官方空间页面提交，逐站点读取 user.qzone.qq.com / h5.qzone.qq.com Cookie，优先匹配更具体的域名并拒绝跨账号组合，不再采用全局 Cookie 回退。

新增两个回归测试覆盖页面就绪条件、Cookie 域优先级、无关子域及账号冲突；125 项 Rust 测试通过。该改动修复了凭证选择问题，仍未通过安装后的真实 QQ 请求验证，不能宣布 501 已解决。

## 结论与下一步

- 当前条件下，历史接口拦截与携带现有账号 Cookie 相关。改变环境代理路径、请求令牌或 TLS 实现，未使保存会话恢复可读。
- 尚未确定是 Cookie 格式、凭证失效、会话风控还是账号针对旧接口的限制；不能宣称账号被封禁或重新登录必然恢复。
- 10 分钟是软件保护等待，不是腾讯解除限制的承诺。此前暂停逻辑减少了重复请求，尚未解决真实会话的访问失败。
- 用户已完成客户端重新登录和官方个人空间登录，不应无条件要求再次重复登录。应区分旧接口受限和整个会话失效，并验证可用数据源的实际覆盖范围。

## 验证边界

`src-tauri/src/qzone_network_diagnostic.rs` 是测试专用模块，不进入安装包。必须显式设置 `QZA_DIAGNOSE_SAVED_SESSION=1` 并运行过滤名 `diagnose_saved_session_http_status_without_exposing_credentials` 的 ignored 测试；不要作为定时任务或 CI 测试。一次最多 11 个有超时和响应体上限的只读请求，不跟随重定向。

常规 Rust 测试 123 项通过；在线诊断单独执行。诊断执行成功只表示采集到响应，不表示恢复成功。本轮没有改变生产请求策略、解除保护等待或重新生成安装包。

## 后续定位：旧接口与桌面动态接口行为不同

增加两个显式 opt-in 的 ignored 测试，不进入发布二进制。仅在 Rust 内读取会话，不输出正文或凭证，不修改本地记录。

- `diagnose_cookie_identity_shape_without_exposing_values`：当前标识符合 QQ 常见的 `o` 加补零数字格式，Cookie 值通过字符合法性检查。在旧历史接口上，普通测试 Cookie 和占位账号标识返回 200；仅携带真实 `uin` 或 `p_uin` 就返回腾讯 WAF 501。不能据此断言账号封禁，但现象并不依赖完整 Cookie 或令牌组合。
- `diagnose_desktop_feeds3_without_exposing_credentials`：参考 [onebot-qzone 的接口说明](https://github.com/Gu-Heping/onebot-qzone/blob/main/doc/feeds3-parser.md)，用相同保存会话请求官方 HTTPS `feeds3_html_more` 首页（scope=0）。实测 HTTP 200、非 WAF，安全对象字面量解析器解码出 7 个含 HTML 的条目，合计约 98 KB。首次通用 JSON 提取器只取到嵌套对象，不能用其缺少顶层 code/data 推断接口空响应；后续以 `history_response::decode` 的结果为准。

这是同一会话可以读取桌面动态的证据，不是旧历史接口恢复正常的证据。scope=0 动态可能包含好友内容，7 个片段不等于 7 条本人已删除的说说。不得把该接口简单替换进历史消息扫描、沿用 offset 断点，或将其成功视为历史恢复完整。该轮排查时生产路径尚未接入该来源，501 根因仍未完全解决。

诊断日志位于工作区外的 `output/501-cookie-shape.log` 和 `output/501-feeds3.log`，仅含状态、长度、计数及布尔值。

## 桌面个人历史通道接入

继续验证 scope=1 后确认：该范围返回 `fct_` 历史互动卡片，能够沿用现有按 QQ 号确认归属的解析器；不是把 scope=0 好友流当作本人历史。使用当前保存会话，正式客户端请求函数已连续读取两页：8 / 9 个卡片，解析出 5 / 4 条归属明确且事件 ID 不重复的历史互动。该计数不表示已删除说说数量。

分页必须同时传递已验证的 `externparam` 数值字段、顶层分页字段和 `pagenum` / `begintime`。缺少这些参数时，实测可能重复返回首页。新的 `desktop_history.rs` 限制 scope=1，检查响应业务码和分页状态，拒绝重复游标；仅保存 offset、total、basetime、feedsource 和 pagenum，不保存 `gdtadvcookie` 或任何令牌。新通道使用独立 `history-desktop-v1` 断点，不复用旧接口的 offset 扫描状态，不删除原有记录。

另发现新通道会间歇返回 `code=-10001, message="network busy"`。程序将其与登录失效、WAF 501 分开：等待 45 秒重试同一页一次（等待可取消），仍失败就暂停并保留断点，保护等待 60 秒后可继续。该失败不会继续轰击移动互动接口，也不会计为空页或跳过页。

默认优先读取已验证的桌面个人历史；仅当新路由返回 404/405 时尝试原有旧历史来源，不在 WAF 后轮换路由。桌面历史完整读取而移动补充接口 501 时，保留部分完成状态和 10 分钟保护等待。旧接口的服务端拦截本身没有被解除，不能承诺所有历史或已删除内容都能取回。

只读在线验收保留为 `verify_production_desktop_history_without_private_output` ignored 测试，每次最多 3 页、每页最多一次繁忙重试（总计最多 6 个请求）；不写用户数据库，不输出正文或事件 ID。探索阶段的临时多路诊断已移除，结果保存在 `output/501-desktop-contracts.log` 和 `output/501-production-desktop.log`。

本轮最终在线验收：第 1 页解析出 5 条归属明确的互动；第 2 页遇到繁忙，等待 45 秒后重试成功，另解析出 4 条新互动；第 3 页繁忙重试后仍未成功，因此三页全通过的验收未通过。该结果验证了实际数据可读及同页退避后可推进，尚未验证整个历史扫描完成、2018 年以前的在线数据覆盖或已安装客户端的端到端写入。没有将失败的在线验收当作通过。

常规 Rust 测试 134 项通过、8 项显式诊断跳过；Windows `cargo check` 和前端类型检查/构建通过。另补充断点统计恢复，避免继续任务时已经读取的页数和记录数重新显示为 0。安装包仍属于本地测试构建，不代表历史接口全程可用。

## REA 对照调研与客户端反馈调整

[REA 浏览器观测文档](https://github.com/morluto/rea/blob/main/docs/browser-observation.md)提供被动请求观测和会话对照方法；[网络捕获文档](https://github.com/morluto/rea/blob/main/docs/web-network-captures.md)支持分析保留的 HAR/SAZ。它们不是 QQ 解限工具。本机没有运行 REA，也没有取得同账号、同一个受限接口在官方网页中成功的网络记录。官方个人空间能展示内容，不能替代这个对照证据。捕获中的 URL 查询参数也可能含凭证，不能原样公开。

[QzoneArchive PR 54](https://github.com/Gaoshu705/QzoneArchive/pull/54)主要增加超时、重试和退避；[对应发行说明](https://github.com/txyyt/QzoneArchive/releases/tag/v1.0.3-txyyt.1)明确不扩大可恢复范围。[历史 501 报告](https://github.com/LibraHp/GetQzonehistory/issues/285)没有给出可验证的稳定解限方案。当前没有找到足以证明本账号限制已解除的方法，不把延长等待或换接口描述成解除服务端限制。

按照用户要求，客户端将已识别的 QQ 501/WAF 和接口繁忙转换成普通读取说明，不展示原始技术报错、告警色或异常前缀。任务仍保留部分读取/暂停状态、断点、计数和保护等待，不标记全部成功。软件授权、真实登录过期、数据库和磁盘错误继续正常提示。原始后端原因仍供开发诊断使用。

新增 `scripts/test-qq-source-notice.mjs` 验证转换边界，前端构建通过。使用真实 TasksView 和合成 IPC，在浏览器验证限制暂停、部分读取、繁忙、登录失效、磁盘错误及启动受限场景；390px 窄屏没有横向溢出。该验收不使用真实 QQ 凭证，不等同于安装后原生客户端或真实手机全量恢复验收。本轮没有重复请求受限接口。
